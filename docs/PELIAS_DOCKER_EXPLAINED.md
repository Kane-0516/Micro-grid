# Pelias、Docker 与本项目部署关系说明

本文档专门回答三个问题：

1. Pelias 是什么
2. 为什么 Pelias 需要额外用 Docker 方式运行
3. 现在整个项目是不是已经全面 Docker 化了

## 1. 先说结论

当前这个仓库并不是“整个项目都必须用 Docker 才能运行”。

更准确地说：

- `frontend/` 可以原生运行
- `backend/` 可以原生运行
- `Pelias` 通常通过 Docker 运行
- `docker-compose.yml` 目前只编排了前端和后端，没有把 Pelias 编进去

所以当前项目是“部分 Docker 化”，不是“全量 Docker 化”。

## 2. Pelias 是什么

Pelias 是一个地理编码系统，用来做：

- 文本地址 -> 经纬度
- 经纬度 -> 地址文本

在这个项目里，Pelias 主要服务于地图相关能力：

- 搜索地点
- 根据点击地图的位置回填地址
- 把经纬度转换成更像“站点名称”的文字信息

注意一点：

前端并不是直接调用 Pelias，而是先调本项目后端的接口：

- `/api/geocode`
- `/api/reverse-geocode`

然后由后端再去访问 Pelias。

也就是说，Pelias 是这个项目的“外部基础服务”，不是前端或后端代码本身。

## 3. 为什么 Pelias 常常要单独跑

原因不是“项目设计得奇怪”，而是 Pelias 本身就不是一个简单的单进程程序。

Pelias 背后通常包含多部分组件，例如：

- API 服务
- Elasticsearch
- 数据导入流程
- 行政区、道路、地址等原始地理数据

这类系统的典型特征是：

- 依赖多
- 数据体量大
- 初始化流程复杂
- 对运行环境要求更高

所以它和你这个项目的前端、后端完全不是一个重量级。

## 4. 为什么 Pelias 常用 Docker 跑，而不是直接本机安装

核心原因是环境复杂度太高，Docker 更容易把它封住。

### 4.1 Pelias 的依赖链比较重

Pelias 不是 `pip install pelias` 或 `npm install pelias` 就能直接工作的那种工具。

它通常涉及：

- Elasticsearch
- 多个导入脚本
- 大量地理数据源
- 索引构建流程
- API 容器

如果全手动装在 Windows 本机上，维护成本会很高。

### 4.2 官方和社区实际使用方式基本都是容器化

这个仓库里的 `pelias/README.md` 也已经明确走的是：

- Docker Desktop
- WSL2
- Pelias Docker 项目

这说明当前项目对 Pelias 的集成思路，不是把 Pelias 当成本仓库内的普通子模块，而是把它当成一个独立服务来接入。

### 4.3 数据导入和重建索引更适合容器化环境

Pelias 最大的工作量常常不在“启动”，而在：

- 下载数据
- 导入数据
- 建索引
- 重建索引

这些操作如果直接散落在本机环境里，会带来：

- 路径混乱
- 版本不一致
- 清理困难
- 迁移困难

Docker 的好处是：

- 服务边界清楚
- 环境可复制
- 清理和重建更容易
- 团队里每个人的运行方式更一致

## 5. 为什么前后端没有像 Pelias 一样强制 Docker 化

因为前后端本身要轻很多。

### 5.1 前端本质就是一个 Vite 开发服务

前端只需要：

- Node.js
- npm install
- npm run dev

这在本机开发体验最好，热更新也更直接。

### 5.2 后端本质就是一个 FastAPI 服务

后端只需要：

- Python
- pip install -r requirements.txt
- python app/main.py

相比 Pelias，后端依赖虽然不少，但仍然是“普通 Python Web 服务”的复杂度，还没有到必须靠 Docker 才能开发的程度。

### 5.3 所以当前仓库形成了一个现实上的分工

就是：

- 前后端在开发时原生跑
- Pelias 作为基础服务用 Docker 跑

这是一个很常见的混合开发形态。

## 6. 那现在整个项目到底是不是 Docker 部署

答案是：目前不是完全 Docker 化。

### 6.1 当前实际存在两种运行形态

第一种，开发形态：

- 前端原生运行
- 后端原生运行
- Pelias 用 Docker 运行

这也是当前仓库最主要的形态。

第二种，半容器化形态：

- 前端用 Docker
- 后端用 Docker
- Pelias 不在 `docker-compose.yml` 内，需要你自己另起

也就是说，当前根目录的 `docker-compose.yml` 并没有把整个系统一次性编排完整。

### 6.2 `docker-compose.yml` 里现在有什么

当前只定义了两个服务：

- `backend`
- `frontend`

没有 `pelias` 服务。

所以如果你问“现在项目是不是整个都用 Docker 部署”，严格答案是：

不是。

准确说法应该是：

- 应用主站可以 Docker 化
- 地理编码基础设施目前是独立管理的
- 开发模式和部署模式还没有被统一成单一方案

## 7. 为什么 `start-all.bat` 还要求 Pelias 先启动

因为这个脚本本身不是“全家桶一键部署脚本”，它只是“本项目应用层一键开发启动脚本”。

它做的事情是：

1. 检查 Pelias 是否已在 `localhost:4000` 提供服务
2. 如果 Pelias 可用，则启动后端
3. 再启动前端

换句话说：

- `start-all.bat` 假设 Pelias 是一个外部前置条件
- 它不负责创建 Pelias
- 它只负责使用已经存在的 Pelias

这也是为什么你会感觉 Pelias 是“额外的一套东西”。

因为它确实就是额外的一套基础设施。

## 8. 如果不用 Pelias，项目还能不能跑

能跑一部分，但不是完整能力。

### 8.1 仍然可用的部分

- 前端页面
- 后端计算接口
- 大多数表单流程
- 优化与结果计算
- 非地图搜索链路

### 8.2 会受影响的部分

- 地点搜索
- 点击地图后自动反查地址
- 地址名回填
- 更完整的地图定位体验

所以 Pelias 对这个项目不是“每个页面都必须依赖”，但对地图定位体验是重要基础设施。

## 9. 什么时候适合继续保持现在这种架构

如果当前目标是：

- 本地开发为主
- 地图功能不是唯一核心
- 团队里有人需要单独维护 Pelias 数据

那现在这种方式其实合理：

- 前后端开发效率高
- Pelias 独立维护
- 出问题时边界清楚

## 10. 什么时候适合把整个项目进一步统一成全 Docker

如果后续目标变成：

- 一台机器一键部署
- 团队成员环境统一
- 测试环境和生产环境更一致
- 想减少“先起这个再起那个”的人工步骤

那就适合再往前走一步：

- 把 Pelias 也纳入统一编排
- 明确初始化和数据卷策略
- 区分开发 compose 和部署 compose

不过这已经不只是“写文档”的问题，而是一次部署架构整理。

## 11. 当前最准确的理解方式

你可以把当前系统理解成三层：

### 第一层：业务应用层

- 前端 `frontend/`
- 后端 `backend/`

这两层是你的 MicroGrid 应用本体。

### 第二层：基础地理服务层

- Pelias

这层不是业务代码本体，但地图功能依赖它。

### 第三层：启动方式

当前支持两类：

- 原生启动前后端
- Docker 启动前后端

但 Pelias 暂时仍主要走它自己的 Docker 流程。

## 12. 对你现在最实用的建议

如果你现在的主要目标是开发和验收这个项目，按下面理解就够了：

1. 这个项目本体不是必须全 Docker 才能跑
2. 前后端都可以原生启动
3. Pelias 因为本身复杂，通常独立用 Docker 跑
4. 根目录 `docker-compose.yml` 目前只覆盖前后端，不覆盖 Pelias
5. 所以当前项目属于“前后端可原生，Pelias 独立容器化”的混合模式

这就是当前仓库的真实状态。

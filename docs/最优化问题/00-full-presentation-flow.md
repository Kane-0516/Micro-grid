## 第 1 节｜开场：对客户、对同事说什么（2 分钟）

### 1.1 对客户（售前话术）

「我们先根据您的 **场地** 算最多能装几套光伏，再结合 **用电情况** 在可装范围内给出几套光储柴方案，用 **全年仿真** 算油耗和回本期，帮您选 **推荐方案**。」

### 1.2 对技术同事（本场主题）

「系统不是一次计算器，而是 **三个（售前）+ 一个（运行期）** 不同性质的优化问题串联；**已知负载** 和 **DIY** 两条向导路径用到的步骤不一样。」

### 1.3 三个最易混淆点（先打预防针）

1. **产品库是多维的**（板型、pack、柴发档）≠ **一次寻优扫多维**（我们主要扫 **套数**）。  
2. **问题 ③** 是「容量已定，排全年调度」≠ **问题 ②** 是「选容量」。  
3. **prediction EMS 附加项** ≠ **④ 已完整上线**（④ 在 EMS 预测服务里建）。

## 第 2 节｜第一步：两种售前场景（5 分钟）

> **目的：** 听众必须先知道「走哪条路」，后面三问题才讲得通。

### 2.1 入口：向导选场景

| 场景 | 客户有什么 | 系统干什么 |
|------|------------|------------|
| **known-load 已知负载** | 年用电量 / 账单 | **自动比** 1…N 套，给推荐/次优/备选 |
| **DIY** | 设备大致已定 | **不自动比套数**，只 **验证** 手选配置 |
| no-load（可一句带过） | 无负荷，早期规划 | 标准托盘配置 |

### 2.2 known-load 完整问题链

```text
选「已知负载」
  → 地点 + 场地（① 可得 max 套数 N）
  → 输入年负荷、柴发、电压、EMS…
  → 点击计算
       → POST /api/optimize   （② + ③，每个套数）
       → 方案选择页
  → 用户选一套
       → POST /api/calculate  （③ 精算 + 报告）
```

**三个客户问题 → 三个优化问题：**

- 能装几套？ → **①**  
- 装几套最划算？ → **②**  
- 一年多少油、会不会断电？ → **③**

### 2.3 DIY 完整问题链

```text
选「DIY」
  → 场地（① 上限 N）
  → 用户手选：套数、逆变器、电池包、柴发
  → 直接 POST /api/calculate（只有 ③ + 经济估算）
```

**关键差异：没有 ②。** 不是系统不想比，是 **没有可靠年负荷，回本期不能当硬优化目标**。

### 2.4 三 / 四问题在两条路上的出现

| 问题 | known-load | DIY |
|------|------------|-----|
| ① 场地 | ✅ | ✅（上限；套数自选 ≤N） |
| ② 选型 | ✅ `/optimize` | ❌ 手选 |
| ③ 运行 | ✅ 每候选 + 精算 | ✅ 一次 calculate |
| ④ 预测调度 | 投运后 EMS | 投运后 EMS |

**记忆：** DIY = **① + ③**；known-load = **① + ② + ③**。

## 第 3 节｜第二步：和 HOMER Pro 对照（4 分钟）

> **目的：** 销售/电气常问 HOMER；说明 **卖的问题类似，算的方法不同**。

### 3.1 相同（流程可对齐）

- 先约束 **PV 能装多少** → 再在范围内配 **储能、柴发** → **全年仿真** → **比经济性**。  
- 都不能从「只知道年用电量」**唯一**推出一套系统（多套架构都可行）。

### 3.2 不同（实现）

| 维度 | HOMER Pro（典型） | 我们 |
|------|-------------------|------|
| PV 上限 | 用户手填搜索表 | **场地 MILP → max 套数** |
| PV 搜索轴 | kW 列表 0,50,100… | **套数 1…N** |
| 储 / 柴 | 常 **独立 Search Space** 或 Optimizer | 套数 → **公式电池**；柴发 **一次请求常固定** |
| 全年运行 | **规则仿真**（负荷跟踪、循环充电） | **PyPSA LP**（更偏数学最优运行） |
| HOMER 外层 | Search Space **网格** 或 Optimizer **智能搜** | **for 套数** 枚举 |

### 3.3 对客户 / 对同事各一句话

- **对客户：** 「流程和 HOMER 一样先定光伏范围再配储能和柴发；我们用地自动算上限，用数学规划算运行。」  
- **对同事：** 「不是 HOMER 克隆；售前是 **MILP + 套数枚举 + PyPSA LP**。」

## 第 5 节｜问题 ① — 一块不规则场地，最多能摆几套支架？（8 分钟）

### 5.1 吸引式问题

**「凹凸多边形、支架不能重叠、还要留间距 —— 怎样摆才能装得最多？」**

### 5.2 定义什么 / 不定义什么

| 定义 | 不定义 |
|------|--------|
| 最多安装 **套数 N** | 年发电量、回本期 |
| 可选：每套摆放位置 | 电池、柴发大小 |

### 5.3 数学是什么

- **0-1 整数规划 MILP**  
- 变量 \(x_i \in \{0,1\}\)：候选位置 \(i\) 是否装一套  
- 目标：\(\max \sum x_i\)  
- 约束：重叠则 \(x_i + x_j \le 1\)  
- 求解器：**HiGHS**（`layout_optimizer._solve_milp_mixed`）

### 5.4 怎么解（流程口述）

1. 输入多边形顶点（地图画场地）或仅面积  
2. 多角度扫描，枚举候选位置（横放/竖放）  
3. 建冲突对 → MILP → HiGHS  
4. 大场地可分区；失败则贪心回退  
5. **仅面积、无多边形** → 启发式 `max_systems_for_area`（**不是** MILP，快但不如多边形准）

### 5.5 系统位置

- API：`POST /api/layout/optimize`  
- 前端：`SiteAreaMap` → `maxBracketSetsByLayout`

### 5.6 与下游关系（必讲）

```text
① 输出 N  →  ② 只搜索 sets = 1, 2, …, N
           →  DIY 用户自选 sets ≤ N
```

**① 只给天花板，不替你选 3 套还是 5 套。**

## 第 6 节｜问题 ② — 在能装的 N 套里，哪套光储柴最值得卖？（10 分钟）

> **仅 known-load。** DIY 跳过本节。

### 6.1 吸引式问题

**「最多只能装 N 套时，装几套、配多少电池和多大柴发，回本期最好、又别太爱断电？」**

### 6.2 定义什么

- **决策：** 离散方案（套数 → PV、pack 数、柴发档等）  
- **目标：** 按 payback / NPV 等 **排序**，标推荐、次优、可靠性风险  
- **不决策：** 每小时发多少电（属 ③）

### 6.3 数学是什么（当前实现）

**不是** 一个大 LP，**不是** HOMER 式 PV×电池×柴发全表笛卡尔积。

```text
for sets = 1 … N:                    ← 唯一主动枚举轴
    PV   = sets × 每套板数 × 板 kW
    电池 = 公式( PV, 储能天数, 日负荷 ) → ceil 到 pack
    柴发 = 请求开始时算一次，各套通常相同
    运行 = ③ PyPSA 或 quick_estimate
    经济性 → score 排序
```

**类型名：** 离散搜索 + 打分排序；每个候选的运行来自 **③**。

### 6.4 柴发、电池为何显得「多维」却是从属

| 变量 | 来源 |
|------|------|
| 套数 | **枚举** |
| PV | **绑套数** |
| pack | **公式 + 产品目录圆整** |
| 柴发 kW | **整次固定**（峰值×1.2 对齐标准档 / 用户指定） |

要对齐 HOMER「多维表」，需 **额外** 枚举 pack × 柴发（改造项，见 01 分享稿）。

### 6.5 怎么解（`optimize_with_diagnostics` 口述）

1. 读产品目录；`effective_max_sets = min(配置, ①的N)`  
2. 定 `diesel_kw`（一次）  
3. 有经纬度：生成 8760h 负荷、PV 曲线；可选纯柴油基准 1 次  
4. `for sets`：公式容量 → PyPSA 或 quick → 经济模型 → score  
5. 候选太多：先 quick 全扫，再 Top ~10 套 PyPSA 精算  
6. 排序输出：方案1推荐 / 方案2次优 / 失负荷风险标签  

- API：`POST /api/optimize`  
- 前端：`useWizardCalculation` → `PlanSelectionPage`

### 6.6 与 ①③ 关系

- **依赖 ①** 的 N  
- **每个候选必须调 ③**（否则油耗、失负荷不可信）  
- 用户选定后 **再调一次 ③** 精算（`calculate`）

## 第 7 节｜问题 ③ — 方案定稿后，一年 8760 小时怎么才最省？（8 分钟）

### 7.1 吸引式问题

**「PV、储、柴发大小都定了，每个时刻怎么发、充放、开油机 —— 怎样排全年最省、又尽量少断电？」**

### 7.2 与 ② 的分工（必讲表）

| | ② 选型 | ③ 运行 |
|---|--------|--------|
| 问 | **买多大** | **怎么用** |
| 容量 | 变（扫套数）或 DIY 手定 | **固定** |
| 数学 | 枚举+排序 | **LP**（8760 联合） |
| 类比 | 配电脑规格 | 全年开机排班表 |

### 7.3 数学是什么

- PyPSA 建网：PV、储能、柴发、负荷、弃光、失负荷  
- 目标：最小化运行边际成本（油、失负荷惩罚等）  
- `n.optimize(solver="highs")`  
- 部分模式 `uc` 为 MIP；常见 `lp`/`cc` 以 LP + 后处理为主  

### 7.4 调度模式（与电气相关）

| 模式 | 含义 |
|------|------|
| `lp` / `lf` | PyPSA 经济调度 |
| `cc` | 循环充电；可用 HOMER 式规则 `_run_homer_style_dispatch` 覆盖柴油结果 |
| `prediction` EMS | 精算时常强制 `lp`（产品方向，仍多为 **全年已知曲线**） |

### 7.5 何时调用 ③

| 场景 | 调用次数（量级） |
|------|----------------|
| known-load optimize | 每精算套数 1 次 + 纯柴油 1 次 |
| 选方案后 calculate | +1 次精算 |
| DIY | calculate 1 次 |

### 7.6 和 HOMER 内层差异

- HOMER：**规则**逐时仿真  
- 我们：**LP**  
- 同容量下曲线可不同 → **机制差异**，不是简单谁更准

## 第 10 节｜问题 ④ — 基于预测的光储柴调度（EMS 预测服务）（10 分钟）

> **为什么放在售前分享里讲：** ④ **也是优化问题**；与 ①②③ **互补**，不是替代。  
> **详稿：** [04_预测调度-讲义.md](./04_预测调度-讲义.md)

### 10.1 吸引式问题

**「不知道明天负荷和光照确切值时，未来 6～24 小时该怎么排光储柴，才能少用油、少断电？」**

### 10.2 和 ③ 的区别（必背表）

| | ③ 售前 | ④ EMS 预测服务 |
|---|--------|----------------|
| 何时 | 卖方案、写报告 | 电站 **投运后** |
| 曲线 | **全年已知**（统计/历史） | **预测**，滚动更新 |
| 频率 | 每方案少量 | 15 min～1 h **持续** |
| 目的 | 回本期、年油耗证据 | 现场省油、可靠 |
| 现网 | `calculate` / `optimize` 内 PyPSA | **待建设** |

**向导 `prediction` addon：** 产品承诺 + 精算走 `lp`（多为全年曲线预览）≠ ④ 已完整落地。

### 10.3 问题 ④ 定义（两层）

```text
【A 预测层】  →  Ŝ_load(t), Ŝ_pv(t)  （EMS 预测服务）
【B 优化层】  →  滚动窗内 min 油费 + 失负荷惩罚 … （问题④本体）
```

### 10.4 EMS 预测服务要做什么（目标架构）

```text
数据采集 → 预测(负荷/PV/天气) → 滚动优化(④) → 下发 EMS → 实测反馈 → 重算
```

容量 **不再重选套数**，用售前 ①②③ 定好的配置。

### 10.5 怎么解（优化层）

| 方案 | 说明 |
|------|------|
| 滚动确定性 LP | 每 15～60 min 用最新预测做 H 小时 LP，执行首段 |
| 多情景随机 LP | 预测多情景，优化期望成本 |
| MPC | 短窗 NLP/QP，分钟级追踪（二期） |

可复用 `OffGridMicrogridSimulator` + HiGHS，改 **snapshots=滚动窗**，曲线由 **预测 API** 注入。

### 10.6 现网 vs 目标（诚实口径）

| | 现网 | 目标 |
|---|------|------|
| 预测 API | ❌ | ✅ EMS 预测服务 |
| 滚动优化 | ❌ | ✅ ④ |
| prediction 产品项 | addon + LP 精算预览 | 与运行能力一致叙事 |

## 第 11 节｜延伸：MPC 与无人机 / 小车寻路（5 分钟）

> **目的：** 与做 **无人机自动寻路** 的同事建立共同语言；说明 MPC 是 **跨领域范式**。

### 11.1 MPC 四步（与领域无关）

```text
预测 → 优化 → 只执行第一步 → 滚动
```

### 11.2 对照表

| | 微电网 ④ | 无人机 / 小车 |
|---|----------|----------------|
| 状态 | SOC、温度 | 位置、速度 |
| 预测 | 负荷、PV | 障碍、风场 |
| 控制 | 充放、柴发 | 加速度、航向 |
| 周期 | 分钟～小时 | 毫秒～秒 |

**一句话：** 都是「在预测的未来里求最优，只走一小步，再算」。

### 11.3 和 ① 场地 MILP 区分

- **①**：静态 —— 摆不摆（一次算完）  
- **④ / 寻路**：动态 —— 随时间滚动  

公司内：**静态组合优化** 与 **动态滚动优化** 两类实践都有。

### 11.4 协作话术

「EMS 预测服务 = **预测模块 + 优化模块 + 闭环**；与寻路团队在 **架构上可对标**，物理模型不同，方法论可交流。」

**不是：** ④ 做空间避障；寻路不算柴发 SOC。

## 第 12 节｜收尾金句（1 分钟）

> **售前：** ① 定上限 → ②（known-load）在 1…N 比方案 → ③ 给全年数字与报告。  
> **投运：** 容量来自售前 → **④** 在 EMS 预测服务里用 **预测 + 滚动优化** 持续调度。  
> **③** 回答「方案好不好」；**④** 回答「建好后每天怎么开更好」。  
> **MPC** 若用于④，与 **无人机寻路** 同范式 —— **问题不同，可横向协作。**
